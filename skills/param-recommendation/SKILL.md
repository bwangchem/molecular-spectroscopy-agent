# param-recommendation

## What this skill does

ORCA parameter recommender for the Molecular Spectroscopy Agent (MSA); it
consumes the task_list produced by smiles-to-xyz and appends a `system_type`, an
orthogonal `need_zora` flag, a `charge` / `multiplicity` pair, and a per-step
`params` recipe to every task. For each task it classifies the molecule from
`task["smiles"]` with RDKit (`functional_basis.detect_system_type`) into one of
three system types — `neutral` / `anion` / `zwitterion` — and independently sets
`need_zora` True only when the molecule contains Br (Z=35) and no I (Z=53); any
I atom vetoes ZORA. It then looks up the per-spectrum ORCA recipe skeleton from the shared
source of truth (`functional_basis.recipe_for(spec, system_type, need_zora,
solvent_model, target_nucleus)`), deep-copies it, and derives the
`charge` / `multiplicity` pair from `functional_basis.SYSTEM_CHARGE_MULT`. The
solvent is resolved as the task's explicit `solvent_std` when present, else the
per-spectrum `functional_basis.DEFAULT_SOLVENT` (gas / empty -> None). It knows no
functional/basis strings itself and defines no local solvent dictionary; the only
chemistry it performs directly is the RDKit charge-class reading.

Supported / unsupported systems (v2.0 scope): all three system classes
(`neutral` / `anion` / `zwitterion`) are closed-shell singlets, so `multiplicity`
is hard-fixed at 1 for every task and `charge` is 0 (neutral / zwitterion) or -1
(mono-anion). Open-shell systems — radicals, triplets, high-spin states and
carbenes — are out of scope this version (deferred to a later release) and are
intercepted upstream (task-recognition rejects open-shell wording; name-to-smiles
rejects odd-electron SMILES), so they never reach this skill.

## Task Field Contract

This skill sits at the **parameters (P1-5)** stage of the pipeline
(stage_id=`params`, upstream=`xyz`).

**Consumes (from xyz):**
- `smiles`: string, the SMILES resolved by name-to-smiles; RDKit reads it here to
  classify the system type and the ZORA flag (an empty SMILES is a fail-soft error).
- `xyz_file`: string, path to the initial geometry generated by smiles-to-xyz
  (carried through; the geometry itself is not read here).
- `target_spectra`: string, one of `ir | raman | uvvis | nmr | fluo | xanes`;
  the key that selects the ORCA recipe via `functional_basis.recipe_for`.
- `solvent_std`: string, the canonical CPCM keyword resolved by task-recognition
  (e.g. `"CPCM(Water)"`); optional — when empty the per-spectrum
  `functional_basis.DEFAULT_SOLVENT` applies (gas phase for IR & Raman).
- `extra_params.target_nucleus`: string, optional; forwarded to `recipe_for` so the
  NMR recipe can select the right nucleus.
- `xyz_status`: string; must equal `"success"` for this task to be processed
  (otherwise the task is skipped).

**Appends (written by this skill, per PIPELINE.md §1.1 P1-5 row):**
- `system_type`: string, the RDKit charge-class classification, one of
  `neutral | anion | zwitterion`.
- `need_zora`: bool, True only when the molecule contains Br and no I
  (orthogonal to `system_type`); stamped onto every step's `zora`.
- `charge`, `multiplicity`: int, derived from
  `functional_basis.SYSTEM_CHARGE_MULT[system_type]` (neutral 0/1, anion -1/1,
  zwitterion 0/1); consumed downstream on every `* xyzfile` line.
- `params`: per-step dict `{"step1": {...}, "step2": {...}, ...}`; each step
  carries `calc_type` / `functional` / `basis_set` / `zora` / `solvent_model`.
- `params_fallbacks`: ordered, bounded list of complete replacement `params`
  recipes. Each item carries `fallback_kind` (`scf_threshold | basis`) and
  `changed_steps`; P2 consumes this list without deriving local retry chemistry.
- `params_status`: string, `"success" | "failed" | "skipped"`.
- `params_error`: string, present only when `params_status == "failed"` (a
  one-line reason, e.g. `unsupported target_spectra: '<spec>'` or an RDKit parse
  failure) or `"skipped"` (`"upstream xyz failed"`).

Rewriting any upstream field is forbidden; appending fields outside this
whitelist is forbidden; modifying `task_id` is forbidden.

## Scripts

`scripts/param_recommendation.py` — CLI entry point.

```
python scripts/param_recommendation.py --input local_workspace/<run_id>/task_list.json --output local_workspace/<run_id>/task_list.json
python scripts/param_recommendation.py --input task_list.json --output task_list.json --manifest manifest.csv --validation-report manifest_validation.csv
```

Arguments:

| Name | Required | Description |
|---|---|---|
| `--input` | yes | upstream task_list JSON path (bare list or `{task_list:[...]}`) |
| `--output` | yes | output task_list JSON path |
| `--manifest` | paired optional | source manifest CSV for diagnostic comparison |
| `--validation-report` | paired optional | output CSV containing only differing values |

`--manifest` and `--validation-report` must be supplied together. The report is
diagnostic only, compares each unique `mol_id` once, and never changes task fields
or `params_status`. Its fixed columns are `mol_id,field,manifest_value,pipeline_value,classification,reason`.

All logs and the `SUCCESS:` / `ERROR:` summary lines go to stderr; the task_list
is written to the `--output` file. This skill is pure standard library (only
`copy` beyond the bootstrap) and imports no heavy dependencies, so `--help`
always works.

## Workflow

1. Load the task_list from `--input` via `common_utils.load_task_list`
   (it accepts both a bare list and a `{task_list:[...]}` wrapper).
2. For each task, check `upstream_ok(task, "xyz")`; if it fails, `mark_skipped`
   (writes `params_status="skipped"`, no `params` / `system_type`).
3. Read `smiles = task["smiles"]`; an empty SMILES is a fail-soft error. Classify
   with `functional_basis.detect_system_type(smiles)` -> `(system_type, need_zora)`;
   an RDKit parse failure raises `ValueError`, caught and turned into
   `params_error`.
4. Resolve the solvent: `solvents.solvent_model_from_std(task.get("solvent_std"))`
   when present, else `functional_basis.DEFAULT_SOLVENT.get(spec, "")` (gas / empty
   -> `None`).
5. Look up `recipe = functional_basis.recipe_for(spec, system_type=..., need_zora=...,
   solvent_model=..., target_nucleus=task["extra_params"].get("target_nucleus"),
   contains_iodine=...)` and the ordered `fallback_recipes_for(...)` list.
   A `None` recipe (unknown spectrum) is a fail-soft error
   (`params_error="unsupported target_spectra: ..."`), never a raised exception.
6. `copy.deepcopy(recipe)` so the shared constant module's return value is never
   mutated in place, then derive `(charge, multiplicity) =
   functional_basis.SYSTEM_CHARGE_MULT[system_type]`.
7. On success write `system_type` / `need_zora` / `charge` / `multiplicity` /
   `params` / `params_fallbacks` via `mark_success`; on any failure write `params_status="failed"` +
   `params_error` via `mark_failed` — never raise.
8. Dump the task_list to `--output` via `common_utils.dump_task_list`.
9. When the paired manifest options are present, write a side CSV comparing
   `charge`, `multiplicity`, and `needs_ZORA`; iodine-only ZORA changes are
   `expected_rule_change`, while all other differences are `mismatch`.

**param-recommendation (this skill)** is step 5: it turns the upstream
`target_spectra` + `solvent_std` into the `system_type` + per-step `params`
recipe that `time-estimation` uses to size the job and that the `orca-{spec}`
calculation stage reads (functional / basis_set / zora / calc_type /
solvent_model) to assemble the ORCA input.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| ImportError: msa_shared | vendored scripts/msa_shared/ missing or bootstrap altered | run `tools/vendor_msa_shared.py sync`; keep the §4.1 self-locating block verbatim |
| exit 2 "msa_contract_version mismatch" | msa_shared/VERSION bumped, skill not synced | update the frontmatter and the `MSA_CONTRACT_VERSION` constant |
| `params_status="skipped"` on every task | upstream `xyz_status` is not `"success"` | fix the smiles-to-xyz stage first |
| `params_status="failed"` with "unsupported target_spectra" | `target_spectra` is not one of `ir/raman/uvvis/nmr/fluo/xanes` | correct `target_spectra` at the task-recognition stage |
| `params_status="failed"` with "smiles is empty" or an RDKit parse error | the SMILES is missing or unparseable, so system_type cannot be classified | check the upstream name-to-smiles / smiles-to-xyz stages |
| a step's `solvent_model` is `None` unexpectedly | `solvent_std` is empty / a gas-phase sentinel | set the intended CPCM solvent at the task-recognition stage |
